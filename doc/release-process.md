## Gridcoin Release Process

### Preparation
 - git checkout staging
 - git pull
 - git merge testnet
 - Update changelog and commit
 - Change version in CMakeLists.txt to [version] and set CLIENT_VERSION_IS_RELEASE to 'true'
 - Run contrib/devtools/debian-changelog-release.sh, then commit CMakeLists.txt and the changelog changes it made (debian/changelog, debian-testnet/changelog) together
   - The script runs in the release checkout and needs dch (devscripts) and dpkg-parsechangelog (dpkg-dev). On a host without them, run it from a Debian or Ubuntu container: `docker run --rm -v "$PWD":/src -w /src debian:stable bash -c 'apt-get update -q && apt-get install -yq --no-install-recommends devscripts dpkg-dev && contrib/devtools/debian-changelog-release.sh; status=$?; chown --reference=. debian/changelog debian-testnet/changelog debian/changelog.dch debian-testnet/changelog.dch 2>/dev/null; exit $status'`
   - The entry it writes says "New upstream release." (an UNRELEASED entry already at the release version is finalized as it stands). The release notes reach the packages as changelog.gz (the upstream CHANGELOG.md), not as text in the Debian changelog entry; mainnet entries up to 5.5.2.0-1 carried them.
   - The OBS source build refuses a tag whose top changelog entry is UNRELEASED or names an upstream version other than the one in CMakeLists.txt, so a release made without the script stops in the build instead of mislabelling the packages.
 - git push

### Merge to master
 - git checkout master
 - git pull
 - git merge --no-ff -S staging   # Merge and sign. Copy changelog into commit message, but remove any brackets as that is a git comment

The changelog can be conveniently generated by the following:

#### Gridcoin maintainers/release engineers, suggestion for writing release notes

 - Write release notes. git shortlog helps a lot, for example:

    git shortlog --no-merges tag1..tag2

 - Generate list of authors:

    git log --format='%aN' tag1..tag2 | sort -ui | sed -e 's/^/- /'

 - This helps for the changelog:
 
    git log --pretty=" - %b %s" --merges tag1..tag2 | sed -e 's/Merge pull request \(#[[:digit:]][[:digit:]]*\) from \([[:print:]][[:print:]]*\)\/[[:print:]]*/\1 (\@\2)/' -e 's/[[:space:]]\{2,\}/ /'

 - git checkout master-test
 - git merge master
 - (Do test builds of master-test to do sanify checks of release. This can be used for actual release build of the Windows builds because it is at the same commit.)
 - git checkout master
 - git push

### Windows signing
Release integrity on Windows is Authenticode, through Microsoft Artifact Signing, with certificates issued
to the release engineer personally. CI signs on release tags only, in the job `windows-sign` that follows the Linux Windows-cross build, under the
GitHub environment `windows-release`. Two repository settings decide who can reach that job: the environment
deploys only for tags shaped like a version (`[0-9]*.[0-9]*.[0-9]*.[0-9]*`), and the tag ruleset "Release tags:
admins only" lets only administrators create or move a tag that starts with a digit, so write access to the
repository is not enough to sign. The job exchanges its OIDC token for an Entra ID
token (`azure/login`, a federated credential, no stored secret) and signs with `jsign`, with the Microsoft
timestamp service, in this order:

 1. `gridcoinresearch.exe`, `gridcoinresearchd.exe` and `gridcoin-service.exe`, before packing;
 2. the elevated scripts under `contrib/windows` (the `.ps1` files);
 3. the uninstaller, through an NSIS finalize hook that exists only when CI provides the signing command;
 4. the installer, last.

The account's identifiers are plain values in the workflow, listed in
[`ci_cd.md`](ci_cd.md#windows-release-signing). In another repository the signing steps print a warning and are
skipped; the build does not fail, and the installer is then unsigned. The deploy job attaches an unsigned `SHA256SUMS` that lists the signed installer.

One-time portal tasks, done by the release engineer:

 - W-1: an Azure subscription and an Artifact Signing account (Basic).
 - W-2: individual identity validation for the account.
 - W-3: a public-trust certificate profile.
 - W-4: an Entra ID app with a federated credential for this repository's `windows-release` environment, and
   the certificate profile signer role for that app. Its identifiers go into the workflow.
 - W-5: in the repository settings, the `windows-release` environment's deployment rule (version tags only) and
   the tag ruleset "Release tags: admins only" (`refs/tags/[0-9]*`, creation and update, administrators exempt).

The signer is pinned in `contrib/windows/release-signer.txt`:

    identity-eku=<OID>
    subject-cn=<name>

`identity-eku` is the identity marker of the certificate profile: an extended key usage entry of the form
`1.3.6.1.4.1.311.97.*` that Artifact Signing gives each certificate profile. It is the same in every
certificate issued from the profile, for the life of the profile, while the certificates themselves last three
days, so a thumbprint cannot be pinned. Deleting the profile and creating another gives a new marker. Every
Public Trust certificate also carries `1.3.6.1.4.1.311.97.1.0`, which identifies no one; the verifier
refuses it as a pin. `subject-cn` is the common name of the signer certificate's subject. Both values come
from a signature made with the profile: `(Get-AuthenticodeSignature <file>).SignerCertificate` shows the
subject and, in its extensions, the extended key usage list. Lint rule 9 checks that the file pins both
keys, each once, and nothing else.

The pin is delivered by the previous installer, so trust is anchored at the first install; a change of signer
or of certificate profile must ship in a release signed by the old one.
`test/lint/lint-windows-scripts.py` checks that the update script checks the signature before it runs the
installer.

Users check a release with `Update-GridcoinCore.ps1`, or with `Test-GridcoinRelease.ps1` for an installer they run
by hand; see [`running-unattended.md` -> *Upgrading (Windows)*](running-unattended.md#upgrading-windows).

### Tag
 - git tag -s [version]  # Paste previous commit message into this commit message
 - git push --tags

### Release
 - Go to https://github.com/gridcoin-community/Gridcoin-Research/releases/new
 - Tag version: [version]
 - Release title: [version], <leisure or mandatory as appropriate>
 - Copy/paste changelog into Description
 - Publish

### Finalize
 - git checkout development
 - git merge master
 - Edit CMakeLists.txt, increment version for development. Commit it.
 - git push

 - git checkout testnet
 - git merge development
 - git push

### Announce the release:
 - Reddit /r/Gridcoin, Discord, Slack, Hive, and Twitter
 - Update title of #gridcoin on IRC

### Testnet pre-release
 - git checkout development
 - git pull
 - With the version in CMakeLists.txt at the version to release (a fourth field other than 0 marks a testnet release), run contrib/devtools/debian-changelog-release.sh (tools and container command under Preparation) and commit the change it made to debian-testnet/changelog
 - git tag [version]-testnet
 - git push --tags
 - Edit CMakeLists.txt, increment version for development. Commit it.
 - git push
